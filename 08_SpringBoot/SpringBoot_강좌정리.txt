5. 용어정리

 1) POJO ( Plain Old Java Object )
   - 일반적으로 오래된 자바 객체 의미.
     특정 플랫폼에 의존하는 자바 객체 대비해서 사용되는 용어.
     따라서 POJO는 특정 환경(플랫폼)에 의존하지 않고 재사용될 수 있음. ( extends 또는 implements )
     ex.
	
	  HttpServlet
		|
		|
           TestServlet <== 모든 환경이 아닌 웹환경에서만 사용되는 클래스로 제한됨.


 2) Spring Bean
   - POJO 기반의 Spring 어플리케이션에서 만든 자바 클래스 의미.

 3) IoC ( Inversion of Control : 제어의 역행 )
  - 필요한 빈(클래스)를 직접 생성하거나 빈간에 사용(접근)을 직접 설정하지 않고
    대신 외부(IoC Container)에서 필요한 빈을 생성하고 사용을 설정해주는 개념.

 4) IoC Container
   - IoC 방법으로 빈(클래스)를 관리한다는 의미에서 IoC Container라고 부름
     IoC 방법으로 빈(클래스)를 관리? 빈을 생성하고 사용할 수 있도록 설정.

   - ApplicationContext 빈이 IoC Container역할 담당함.

   ex.
        BeanFactory (인터페이스)
	   |
	   |
	   |
        ApplicationContext(인터페이스)
	   |
	   |
	   |
	  AnnotationConfigApplicationContext ( Java SE환경의 IoC Container )
	  GenericXmlApplicationContext      ( Java SE환경의 IoC Container )
	  .. 
	  XXXWebApplicationContext     ( Java EE환경의 IoC Container )


 5) 의존성 주입 ( Dependency Injection : DI )
  https://docs.spring.io/spring-framework/reference/6.2/core/beans/dependencies/factory-collaborators.html

   -개념: 임의의 클래스에서 다른 클래스를 참조할 때,
        직접 생성해서 참조하는 것이 아니고 외부에서 생성한 후에 생성자 또는 setter메서드를 이용해서 설정해서 사용하는 방법을 의미함.

    가. 생성자 주입( Constructor-based Dependency Injection) - 권장

	  ex. 
	     BoardListServlet     BoardServiceImpl               BoardDAO
				   
				       BoardDAO dao;

					// 생성자 주입
					public BoardServiceImpl(BoardDAO dao) {
						this.dao = dao;
					}

				

		# BoardListSevlet에서 생성했는데. 이 역할이 IoC Container 역할임
		BoardService service = new BoardServiceImpl(new BoardDAO());
	



    나. set 메서드 주입 (Setter-based Dependency Injection)

     BoardListServlet     BoardServiceImpl               BoardDAO
				   
				       BoardDAO dao;
				

					// setter 메서드 주입
					public void setDao(BoardDAO dao) {
						this.dao = dao;
					}

		# BoardListSevlet에서 생성했는데. 이 역할이 IoC Container 역할임
		BoardService service = new BoardServiceImpl();
		service.setDao(new BoardDAO());	

    다. 필드(변수) 주입 ( Field Dependency Injection) 

         BoardListServlet     BoardServiceImpl               BoardDAO
				   

					@Autowired
				       BoardDAO dao;

1. Spring Boot 등장

    - 2016년 등장
    - 기존 Spring Framework에서는 개발자가 처리해야 되는 많은 설정이 있었음.
      ( ex. DB 연동(4가지 설정정보, 드라이버 빌드패스,...) Tomcat 설치 등 ..)
      실제로는 비즈니스 로직에 집중해야함에도 불구하고 위 작업들을 명시적으로 설정했음. 
      즉, 집중이 분산됨.

    - 이러한 문제를 해결하기 위해서 Spring Boot 서브 프로젝트가 진행됨.

2. Spring Boot 특징

   가. 라이브러리 관리 자동화 : 빌드도구(build tool) + starter(*.jar파일들의 모임) 개념을 이용하여 의존성(*.jar) 자동 관리 지원.
   나. 설정 자동화 : 특정 starter(*.jar)를 설정하면 SpringBoot가 알아서 자동으로 환경설정을 맞춰줌.
                ex. XXX-starter-web 설정하면 자동으로 내장 tomcat을 설치해줌.
   다. 독립적으로 실행한 jar 지원.     
      - Java SE환경: 어플리케이션 개발후 배포하기 위해서 jar 파일로 압축함.(빌드 한다고 함)
      - Java EE환경: 어플리케이션 개발후 배포하기 위해서 war 파일로 압축함.(빌드 한다고 함)

     ==> Java SE환경 및 Java EE환경 모두 jar로 압축함(********************)
        
	java -jar XXXX.jar <=== 만약에 웹이라면 자동으로 설치된 내장 tomcat으로 실행됨.

   라. 설정정보는 xml(기존 스프링 및 서블릿/jsp) 대신에 *.properties 또는 *.yml(yaml) 이용.
	

3. 빌드도구(build tool)

   -전체 개발프로세스에서 필요한 작업을 자동화하는 도구.

   개발프로세스는 일반적으로 다음과 같다.

   환경설정   ------> 코드작성 ---> *.jar다운+빌드패스 + 구현----> 테스트(단위테스트,junit5)---> 빌드(압축) ---> 배포
   (jdk설치, 
   tomcat설치)               <------------------------------------------------------------>
                                         자동화

  - 종류

    가. Maven
       - 설정정보가 xml로 되어 있음.

    나. Gradle (*)
       - 설정정보가 build.gralde로 되어 있음.

6. Application 파일

   - src/main/java 에 저장되고 필수 파일임 ( 웹어플리케이션 개발에도 필수 )
   - 역할: 시작점 역할 + @SpringBootApplication 기능


   - @SpringBootApplication는 다음 3가지 어노테이션을 포함함.
https://docs.spring.io/spring-boot/3.5/reference/using/using-the-springbootapplication-annotation.html


     가. @EnableAutoConfiguration 
        - 자동으로 Configuration(환경설정) 설정하는 기능.
	  즉, build.gradle에 등록된 의존성을 보고, 그에 알맞은 최적의 설졍정보를 자동으로 지원함.
	  ex. xxx-starter-web 을 설정하면 자동으로 tomcat 설치 및 웹 어플리케이션 개발하기 위한 환경이 자동으로 설정됨.

     나. @ComponentScan
        - 자동으로 빈(클래스)를 찾아서 new 해줌.
	- 반드시 다음 2가지 규칙으로 되어있어야 됨.
	  a. XXXApplication.java (@SpringBootApplication 포함)의 패키지와 같거나 또는 서브패키지로 되어 있어야 됨.
          b. 마킹해야됨.
              -@Component ( 범용적 )
	      -@Controller
	      -@Service
	      -@Repository
	      -@RestController
	      -@Configuration
	      ..

     다. @SpringBootConfiguration 
      
       - 자동으로 설정되는 기본설정(ex. tomcat포트번호가 8080)이 있고 
        추가로 개발자가 설정이 가능함.
       - @Configuration + @Bean 사용해서 추가로 설정함.
       - 용도: 외부라이브러리라서 수동으로 생성해야 되는 경우가 있음.

        ex.  Test.java 생성

	  @Configuration
	  public class CustomerConfigurtion{

	      @Bean
	       public Test create(){
	         return new Test();
	       }

	  }

1. 빈생성 방법

 1) 권장 패키지 방법 ( 추천 )

   -개념:
      @SpringBootApplication를 가진 빈의 패키지와 같거나 서브패키지로 만들면 자동으로 빈으로 등록되어 생성됨.

   -구현방법 2step

     step1: @SpringBootApplication를 가진 빈의 패키지와 같거나 서브패키지로 만들면 자동으로 빈으로 등록
     step2: 자동으로 생성할 빈을 지정
           @Component ( 범용적 )
	   @Service   ( 서비스 레이어 )
	   @Controller ( 서블릿 역할 )
	   @RestController ( 서블릿 역할 )
	   @Repository ( DAO 레이어 )
	   @Configuration ( 설정정보 추가)

   - 다양한 어노테이션을 사용하는 이유?
     가.프레임워크에게 명시적으로 의도한바를 더 자세하게 알려줌.
     나.AOP 사용시 부가적인 작업을 더 자세하게 설정할 수 있음.


 2) 다른 패키지로 만든 경우

   - 패키지명으로 알려줘야됨.
    
     //@SpringBootApplication(scanBasePackages = {"com.other"})

3. 빈의 scope
https://docs.spring.io/spring-framework/reference/core/beans/factory-scopes.html#page-title

 1)개념
   ApplicationContext(IoC Container)가 생성한 빈은 싱글톤(singleton)으로 실행됨. (기본)

  singleton: 기본, 단 한번만 생성, 여러 사용작 공유 가능
  prototype: 요청할 때마다 매번 생성. 여러 사용자가 공유 불가

  request: HttpServletRequest ( 요청 ~ 응답 )
  session: HttpSession ( 웹브라우저와 동일 )
  application:  ServletContet ( tomcat )


  3)문법

    @Scope("singleton")

4. PRG 패턴 ( Post-Redirect-GET 패턴 )

   1) 개념
     POST 요청에 대해서 Get 요청으로 다시 redirect 처리하는 패턴.
     즉 post 로 시작해서 get 으로 끝나게 하는 방식.
     
     멱등성: 여러번 실행해도 결과가 동일함을 의미함.

              요청시 method:GET
      브라우저 ---------------------->
	 
	      - 조회할 때 (select 작업 )
	      - 멱등성을 가짐.
	      - 새로고침을 여러번 해도 서버에 영향이 없음.

     
              요청시 method:POST
      브라우저 ---------------------->

              - 생성/수정/삭제 때 ( insert/update/delete 작업 )
	      - 멱등성 없음.
	      - 새로고침을 여러번 하면 서버에 영향이 있기 때문에 항상 경고창으로 재요청이 맞는지 확인필요.


   2) POST로 최종 종료되었을 때의 문제점
     
      -새로고침하면 동일한 요청이 연속적을 보내지는 멱등성 이슈 발생
      -URL 복사해서 다른 브라우저에서 요청하면 연결이 안되는이슈 발생

       
        @GetMapping("/main")
       public String  hello4(){
        return "main";
       }

// 그냥 post로 끝난 경우
       @PostMapping("/write")
       public String  write(){
        return "write";
       }

 
// PRG 패턴
       @PostMapping("/write")
       public String  write(){
        return "redirect:success";
       }

        @GetMapping("/success")
       public String  hello4(){
        return "main";
       }

7. 예외처리

   1) 개념
     - 스프링에서 발생되는 예외는 항상 RuntimeException 계열임. (***********)

     - RuntimeException 계열의 예외가 발생되면 항상 호출한곳으로 예외가 전달됨.
      따라서 DAO에서 발생되거나 Service에서 발생되거나 항상 예외는 Controller로 모임.
      결국 Controller에서 예외처리를 하면 됨.(***************************)

     - Controller에서는 try~cacth 가 아닌 어노테이션 이용(선언적 예외처리)
       ( @ExceptionHandler 이용)
 			  
    웹브라우저 ---------->서블릿--------------------------> Controller----->Service ---->DAO
                     (Dispatcher<------------------            <----         <----
		     Servlet)         

		       |
		       |
		       |
	<--------   main.html
	  
	
   2) 예외처리 종류 2가지


    가. 로컬
       - 특정 Controller내에서 발생된 예외만 처리가능.

       구현:
          
           @Controller

			return "main";

		    @GetMapping("/main2")
		    public String  main2(){
			System.out.println("main2");

			//예외발생

		    //로컬

		    //2가지 기능: View+Model

		    // @ExceptionHandler(value=IllegalArgumentException.class)

1. SpringSecurity

   1) 개요
    
    사용자의 인증(Authentication, 로그인 처리) 처리 및 리소스의 접근제어(Authorization, 권한)를
    매우 쉽게 제공하는 서브 프로젝트임.

   2) 용어 정리
     
      - Principal: 접근하는 사용자,  ex. userid,email
      - Credential: 비번
      - Authorities : 권한집합

      - Authentication: 인증
      - Authorization: 인가(권한)

  3) SpringSecurity 특징
   
     - 자동으로 login과 logout 지원
     - username 의미는 Principal임 ( 일반적으로 사용하는 사용자명이 아님 )
     - 회원가입시 반드시 비밀번호는 암호화 필수 (*******************)
     - 로그인시 id만 존재여부 확인하고 비번은 SpringSecurity가 자동으로 체크해줌( SpringSecurity6 부터 지원 )
     - 세션에 저장된 정보를 참조하기 위해서는 @AuthenticationPrincipal 어노테이션을 사용함.
     - Filter기반으로 인증과 인가를 처리함.
       개발자가 커스터마이징이 가능(******************)

1. REST ( REpresentational State Transfer : 표현 상태 전송)
  
   1) 개념
      -웹어플리케이션을 개발하는 방법론중 하나.
      -클라이언트(ex. 웹브라우저,핸드폰,자동차,냉장고,...)와 서버간의 상태정보를 표현하는 방법임.

   2) 이전 방식인 SOAP와 비교

    (1)전체적인 아키텍처 차이점
   
     가. SOAP 방식
       
                  요청
               ------------> 
         클라이언트              서버 ( 서블릿,JSP,Thymeleaf)
        (웹브라우저)         
              <--------------
	          응답(html) <====== 하나의 페이지(화면)로 응답


     나. REST 방식

                    요청(JSON/XML)
               ------------> 
         클라이언트              서버 (  @Controller+@RequestBody  <== 요청처리( JSON--> Java)
	                           @Controller+@ResponseBody <== 응답처리 ( Java --> JSON ) 
				   @RestController = @Controller+@ResponseBody
        (웹브라우저,
	 자동차,핸드폰,
	 ,,)         
              <--------------
	          응답(JSON/XML) <== 하나의 데이터(JSON)로 응답. 따라서 화면이 필요없음.

    (2) 클라이언트 요청 차이점

          가. SOAP 방식

		-GET: SELECT 할때, 명등성 존재
		      @GetMapping
		-POST: INSERT ( 멱등성 존재안함)
		       DELETE (명등성 존재)
		        UPDATE (명등성 존재)
		      @PostMapping
               
	       <form method="get|post">

	  나. REST 방식

	        -GET: SELECT 할때, 명등성 존재
		      @GetMapping

		-POST: INSERT ( 멱등성 존재안함)
		       @PostMapping

		-DELETE :  DELETE (명등성 존재)
			@DeleteMapping

		-PUT    : UPDATE (명등성 존재)
			  전체데이터 모두 수정.
			@PutMapping

		-PATCH  : UPDATE (명등성 존재)
		          데이터 일부분만 수정
			@PatchMapping
  
             ==> 위와 같이 요청할 수 있는 도구가 필요함. ex. curl, postman, Talend API Tester(크롬 플러그인)
